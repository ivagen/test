# Контракт подій WebSocket

## Точка підключення

Клієнти підключаються до того самого origin за адресою `/ws`; зворотний проксі виконує
оновлення (upgrade) з'єднання. Локально через HTTP використовується `ws`, у розгорнутому
середовищі через HTTPS — автоматично `wss`, завдяки відносному URL. Браузерні клієнти
ніколи не підключаються безпосередньо до порту воркера.

## Подія від сервера

```json
{
  "eventId": "6db69aac-0f19-47f0-a24c-c57af9cf0d16",
  "type": "item.updated",
  "itemId": 12,
  "item": {"id": 12, "name": "Updated name"},
  "occurredAt": "2026-07-25T15:00:00Z"
}
```

Для `item.deleted` поле `item` дорівнює `null`. Події публікуються лише після успішної
фіксації транзакції в базі даних. Доставка здійснюється «за можливості» (best-effort) і
може дублювати або пропускати повідомлення.

## Правила для клієнта

1. Запитувати `/api/items` під час початкового завантаження.
2. Застосовувати відому валідну подію ідемпотентно.
3. У разі перепідключення, некоректного вмісту, невідомого типу або неоднозначності —
   повторно запитувати `/api/items`.
4. Перепідключатися з експоненційним зростанням затримки та джитером, з обмеженням
   у 30 секунд.
5. Показувати неблокуючий індикатор погіршеного режиму, поки з'єднання відсутнє; операції
   CRUD залишаються доступними.

## Перевірка живучості

Використовувати протокольні ping/pong там, де їх підтримує обраний сервер. Повідомлення
живучості на рівні застосунку, якщо вони потрібні через обмеження браузера, МУСЯТЬ мати
окреме версіонування та ігноруватися логікою обробки стану елементів.
